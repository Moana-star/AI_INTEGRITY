# Controlled Institutional Data Onboarding

**Purpose:** Populate EIMS with institution-authorized records. This pack contains blank CSV templates and a validation-first importer. It does not contain sample student data or fabricated university records.

**Branch:** `feature/eims-institutional-completion`

## Important: real data and release status

The repository is a development system, not an approved production deployment. This onboarding path does not make it production-certified. Before live student data is loaded, the institution must authorize the processing, approve the data source and retention rules, and complete the security/privacy acceptance gates in [Institutional Integration and Production Acceptance](INSTITUTIONAL_INTEGRATION_AND_PRODUCTION_ACCEPTANCE.md).

- Do not put real student names, admission numbers, phone numbers, email addresses, staff details, credentials or exports in GitHub.
- Keep completed CSV files outside the repository in an institution-approved, access-controlled location.
- Use only a Registrar/authorized source-system export. Do not invent records or treat old demo records as authoritative.
- Back up the target database before any import. Preserve the backup.
- The importer is additive only: it refuses duplicates and never updates or deletes existing records.
- Dry-run is the default. No write occurs without `--apply`.
- Student records continue to use the protected Institutional Registry CSV import or approved registry workflow. This utility imports units, venues and unit enrolments linked to existing student admission numbers.
- No session, candidate, invigilator assignment, attendance event, incident, eligibility decision, biometric record or payment/fee decision is generated by this utility.

## Files in this pack

| Template | Required columns | Purpose |
|---|---|---|
| `templates/institutional_import/students.csv` | admission_number, first_name, last_name, course, year_of_study, faculty, department, institutional_email, phone, academic_status, academic_year, semester | Existing Registry student CSV import |
| `templates/institutional_import/academic_units.csv` | unit_code, unit_name, department, faculty | Authoritative unit catalogue |
| `templates/institutional_import/venues.csv` | venue_code, building, room_name, capacity | Approved examination venues |
| `templates/institutional_import/student_unit_enrolments.csv` | admission_number, unit_code, academic_year, semester | Actual student registrations |

The files contain headers only. Replace them with authorized records in a secure location; never commit populated files.

## Recommended order

1. Confirm written authorization, data owner, academic year/semester definitions, source-system export date and responsible Registrar/ICT contacts.
2. Back up the target database and verify the backup can be opened.
3. Initialize the application schema by starting the app and opening the Institutional Registry and Academic Operations pages once.
4. Review the existing student register. Import only the institution-approved student export through the Registry's CSV import screen. Reconcile row counts and rejected rows with the Registrar before proceeding.
5. Complete the blank academic-unit, venue and enrolment templates using the institution's authoritative records.
6. Run the operations importer in dry-run mode.
7. Resolve every validation error at the source. Do not bypass validation or change admission numbers to force a match.
8. Have the authorized data owner review the proposed counts and source files.
9. Apply the import with an existing authorized staff account ID.
10. Reconcile the resulting database counts and audit events against the signed source export. Retain the import report and source checksum under institutional policy.

## Dry-run

From the repository root (PowerShell):

```powershell
python scripts/import_institutional_operations.py `
  --units-csv C:\EIMS-Private\academic_units.csv `
  --venues-csv C:\EIMS-Private\venues.csv `
  --enrolments-csv C:\EIMS-Private\student_unit_enrolments.csv
```

Dry-run validates:
- required columns, formats, limits and duplicate keys inside each file;
- existing unit and venue code conflicts;
- every enrolment's admission number against an existing student;
- active student status;
- unit references against active existing units or units in the same import;
- existing duplicate enrolments.

It prints counts and rolls back. A successful dry-run is not an authorization decision or proof that the source data is correct.

## Apply

Only after review and backup, use the numeric ID of the authorized administrator or registrar/examination officer already provisioned in the target database. The actor's role is checked against the records being imported.

```powershell
python scripts/import_institutional_operations.py `
  --units-csv C:\EIMS-Private\academic_units.csv `
  --venues-csv C:\EIMS-Private\venues.csv `
  --enrolments-csv C:\EIMS-Private\student_unit_enrolments.csv `
  --apply `
  --actor-user-id 1
```

Replace `1` with the verified account ID. Do not assume the first account has the right role. The importer records each created record in `audit_events` and commits the batch as one transaction. If any write fails, the transaction is rolled back.

If the database is PostgreSQL, set `DATABASE_URL` in the process environment using the institution's approved secret-management method. Do not put the connection string in the command, CSV, repository or chat. The `--database` option is for SQLite and is ignored when `DATABASE_URL` selects PostgreSQL.

## After import

- Reopen Registry and Academic Operations and verify the imported records.
- Re-run the read-only database inspection script.
- Confirm expected row counts and zero foreign-key violations.
- Create examination sessions only from approved examination master records, current unit registrations, confirmed venues, and approved schedules.
- Evaluate eligibility using the effective, approved institutional policy and authoritative source evidence. Enrolment alone must not be treated as fee clearance or exam eligibility.
- Assign invigilators through the application and confirm the required staffing/venue checks.
- Test attendance only with authorized test candidates until the institution approves live operations.

## Known boundaries

- This is not a live SIS, finance, HR or identity-provider integration.
- The utility does not create or update student records; the Registry workflow handles those.
- It does not bulk-create sessions, candidate lists or invigilator assignments.
- Face matching remains disabled until the provider and institutional approvals are complete.
- Production readiness, independent security review, versioned schema migrations, backup/restore drills and formal institutional acceptance remain separate release gates.
